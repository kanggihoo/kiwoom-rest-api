# 종목 가격 알림 서비스용 API 읽기 가이드

이 문서는 키움 REST API로 종목별 가격 정보를 주기적으로 조회하고 알림을 보내는 서비스를 만들 때 먼저 봐야 할 문서를 정리한 것입니다.

전제는 WebSocket 실시간 수신이 아니라, 1분/5분/1시간 같은 주기로 REST API를 폴링하는 방식입니다.

## 결론

처음 구현은 다음 순서가 가장 현실적입니다.

1. 접근토큰 발급
2. 관심종목정보요청으로 여러 종목 현재가 조회
3. 필요할 때만 분봉차트 또는 시세표성정보 추가 조회
4. 1700 오류를 기준으로 호출 속도 자동 감속
5. 나중에 실시간성이 필요해지면 WebSocket 주식체결로 전환

## 1순위: 인증

### 접근토큰발급

- 문서: [001-au10001.md](apis/001-au10001.md)
- API ID: `au10001`
- URL: `/oauth2/token`
- 용도: `appkey`, `secretkey`로 접근토큰 발급

모든 조회 API는 `authorization: Bearer <token>` 헤더가 필요합니다. 공식 이용안내 기준 접근토큰은 24시간마다 재발급이 필요하므로, 서비스에서는 토큰 만료 전에 자동 갱신하는 구조가 필요합니다.

### 접근토큰폐기

- 문서: [002-au10002.md](apis/002-au10002.md)
- API ID: `au10002`
- URL: `/oauth2/revoke`
- 용도: 더 이상 사용하지 않는 토큰 폐기

초기 구현에서는 필수는 아니지만, 운영 종료나 키 교체 플로우를 만들 때 봅니다.

## 2순위: 여러 종목 현재가 조회

### 관심종목정보요청

- 문서: [087-ka10095.md](apis/087-ka10095.md)
- API ID: `ka10095`
- 분류: `종목정보`
- URL: `/api/dostk/stkinfo`
- 추천도: 가장 높음

가격 알림 서비스의 1차 조회 API로 적합합니다.

Request의 `stk_cd`에 여러 종목코드를 `|`로 구분해서 입력할 수 있습니다.

예:

```json
{
  "stk_cd": "005930|000660|035420"
}
```

응답에서 우선 사용할 필드는 다음입니다.

| 필드 | 의미 | 사용처 |
| --- | --- | --- |
| `stk_cd` | 종목코드 | 종목 식별 |
| `stk_nm` | 종목명 | 알림 메시지 표시 |
| `cur_prc` | 현재가 | 목표가/현재가 알림 |
| `base_pric` | 기준가 | 기준 가격 |
| `pred_pre` | 전일대비 | 변화량 알림 |
| `flu_rt` | 등락율 | 등락률 알림 |
| `trde_qty` | 거래량 | 거래량 조건 |
| `trde_prica` | 거래대금 | 거래대금 조건 |
| `sel_bid` | 매도호가 | 호가 알림 |
| `buy_bid` | 매수호가 | 호가 알림 |
| `cntr_tm` | 체결시간 | 데이터 최신성 확인 |

초기 서비스는 이 API 하나로 충분히 시작할 수 있습니다.

## 3순위: 단일 종목 상세 시세

### 시세표성정보요청

- 문서: [012-ka10007.md](apis/012-ka10007.md)
- API ID: `ka10007`
- 분류: `시세`
- URL: `/api/dostk/mrkcond`

단일 종목의 현재가, 전일종가, 거래량, 거래대금, 10단계 호가, 예상체결가까지 넓게 봐야 할 때 사용합니다.

`ka10095`보다 응답 필드가 많고 단일 종목 조회에 가깝기 때문에, 모든 종목을 매번 이 API로 조회하는 구조는 비효율적입니다. 특정 종목이 알림 조건 근처에 왔을 때 추가 확인용으로 쓰는 편이 낫습니다.

### 주식호가요청

- 문서: [009-ka10004.md](apis/009-ka10004.md)
- API ID: `ka10004`
- 분류: `시세`
- URL: `/api/dostk/mrkcond`

호가 잔량, 매도/매수 호가 단계를 자세히 봐야 할 때 사용합니다.

가격 알림만 필요하면 우선순위는 낮습니다. 호가 기반 조건, 예를 들어 “매수 1호가가 특정 가격 이상” 같은 기능을 만들 때 봅니다.

### 일별주가요청

- 문서: [083-ka10086.md](apis/083-ka10086.md)
- API ID: `ka10086`
- 분류: `시세`
- URL: `/api/dostk/mrkcond`

일별 OHLCV가 필요할 때 사용합니다.

장중 실시간성보다는 전일 대비, 최근 N일 기준 조건, 일봉 기반 알림을 만들 때 적합합니다.

## 4순위: 분봉 기반 알림

### 주식분봉차트조회요청

- 문서: [077-ka10080.md](apis/077-ka10080.md)
- API ID: `ka10080`
- 분류: `차트`
- URL: `/api/dostk/chart`

분 단위 가격 조건을 만들 때 봅니다.

Request의 `tic_scope`는 다음 값을 지원합니다.

| 값 | 의미 |
| --- | --- |
| `1` | 1분 |
| `3` | 3분 |
| `5` | 5분 |
| `10` | 10분 |
| `15` | 15분 |
| `30` | 30분 |
| `45` | 45분 |
| `60` | 60분 |

응답에서 우선 사용할 필드는 다음입니다.

| 필드 | 의미 |
| --- | --- |
| `cur_prc` | 해당 분봉 종가 |
| `trde_qty` | 거래량 |
| `cntr_tm` | 체결시간 |
| `open_pric` | 시가 |
| `high_pric` | 고가 |
| `low_pric` | 저가 |
| `pred_pre` | 전일대비 |
| `pred_pre_sig` | 전일대비 기호 |

분봉 API는 종목별 호출이 필요하므로 감시 종목이 많을수록 호출 수가 빠르게 늘어납니다. 기본 가격 알림은 `ka10095`로 처리하고, 분봉 조건이 필요한 종목에만 `ka10080`을 추가 호출하는 구조가 좋습니다.

## 권장 폴링 전략

### 소규모 감시

감시 종목이 1~30개 정도라면 다음 구조로 시작합니다.

```text
매 1분:
  ka10095 관심종목정보요청
  -> 모든 감시 종목 현재가 수집
  -> 조건 판단
  -> 필요한 경우 알림 발송
```

### 중간 규모 감시

감시 종목이 많아지면 종목을 배치로 나눕니다.

```text
watchlist = [종목 1..N]
batch_size = 실측으로 결정
interval = 60초

매 interval:
  watchlist를 batch_size 단위로 분할
  각 배치를 일정 간격으로 순차 호출
```

예를 들어 120개 종목을 4개 배치로 나누면, 1분마다 4번 호출하는 구조가 됩니다.

### 상세 조회는 조건부로만

```text
ka10095 결과에서:
  목표가 근처
  등락률 조건 근처
  거래량 급증
  데이터가 이상함

이 경우에만:
  ka10007 또는 ka10080 추가 호출
```

모든 종목에 상세 API를 매번 붙이면 호출량이 쉽게 커집니다.

## Rate Limit 정리

현재 공식 PDF에서 확인되는 제한 관련 내용은 다음입니다.

- 문서: [error-codes.md](error-codes.md)
- 오류코드: `1700`
- 메시지: `허용된 요청 개수를 초과하였습니다. API ID={?}`

즉 요청 제한은 존재합니다. 다만 추출한 공식 PDF와 공개 공식 가이드에서 초당/분당 정확한 호출 수치는 확인되지 않았습니다.

따라서 구현에서는 정확한 숫자를 하드코딩하지 말고 설정값으로 분리해야 합니다.

초기 권장값:

```text
REST 조회 호출: 초당 1~3회 이하로 시작
토큰 발급 호출: 초당 1회 이하
1700 오류 발생: 즉시 감속
동일 종목 동일 조건 알림: 쿨다운 적용
```

운영 중 실제 응답을 보고 다음 값을 조정합니다.

```text
KIWOOM_MAX_REQUESTS_PER_SECOND
KIWOOM_BATCH_SIZE
KIWOOM_POLL_INTERVAL_SECONDS
KIWOOM_BACKOFF_SECONDS
KIWOOM_ALERT_COOLDOWN_SECONDS
```

## 1700 오류 처리 정책

`1700`이 발생하면 일반 실패로 보지 말고 호출량 제어 이벤트로 처리합니다.

권장 동작:

1. 현재 API ID의 호출을 즉시 중단합니다.
2. 백오프 시간을 적용합니다.
3. 다음 호출부터 초당 호출 수를 낮춥니다.
4. 같은 오류가 반복되면 배치 크기를 줄입니다.
5. 관리자에게 rate limit 경고를 보냅니다.

예:

```text
초기: 3 req/s
1700 발생
-> 30초 대기
-> 1 req/s로 감속
-> batch_size 50에서 20으로 축소
```

## 알림 중복 방지

가격 알림 서비스에서 API 호출량만큼 중요한 것이 중복 알림 방지입니다.

최소한 다음 상태를 저장합니다.

| 값 | 설명 |
| --- | --- |
| `last_price` | 마지막 조회 가격 |
| `last_notified_price` | 마지막 알림 가격 |
| `last_notified_at` | 마지막 알림 시각 |
| `last_condition_key` | 마지막으로 만족한 조건 |

예:

```text
삼성전자 현재가 >= 80000 조건

09:10 80100 -> 알림 발송
09:11 80200 -> 쿨다운 중이면 발송 안 함
09:30 79900 -> 조건 해제
10:05 80100 -> 다시 조건 진입, 알림 발송 가능
```

## MVP API 흐름

```text
서비스 시작
  -> au10001 접근토큰 발급
  -> ka10099 종목 목록 로드 또는 로컬 캐시 사용
  -> 사용자가 등록한 종목을 ka10100으로 검증

스케줄러 실행
  -> ka10095로 감시 종목 현재가 조회
  -> 알림 조건 평가
  -> 필요 시 ka10080 또는 ka10007 추가 조회
  -> 알림 발송
  -> 조회 결과와 알림 상태 저장

오류 발생
  -> 1700이면 호출 속도 감속
  -> 토큰 오류면 토큰 재발급
  -> 네트워크 오류면 재시도와 백오프
```
