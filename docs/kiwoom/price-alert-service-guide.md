# 종목 가격 알림 서비스용 API 분석 가이드

이 문서는 키움 REST API로 종목별 가격 정보를 주기적으로 조회하고 알림을 보내는 서비스를 만들 때 필요한 API 문서를, 실제 링크된 `.md` 원문 기준으로 다시 정리한 분석 가이드입니다.

전제는 WebSocket 실시간 수신이 아니라, 1분/5분/1시간 같은 주기로 REST API를 폴링하는 방식입니다.

## 결론

가격 알림 MVP는 다음 조합으로 시작하는 것이 가장 단순합니다.

1. [001-au10001.md](apis/001-au10001.md)로 접근토큰 발급
2. [089-ka10099.md](apis/089-ka10099.md)로 시장별 종목 마스터 캐시 구성
3. [090-ka10100.md](apis/090-ka10100.md)로 사용자가 등록한 종목 검증
4. [087-ka10095.md](apis/087-ka10095.md)로 감시 종목 현재가 일괄 조회
5. 조건 근처 종목만 [077-ka10080.md](apis/077-ka10080.md), [012-ka10007.md](apis/012-ka10007.md), [009-ka10004.md](apis/009-ka10004.md)로 보강 조회
6. [error-codes.md](error-codes.md)의 `1700` 오류를 호출량 제어 이벤트로 처리

## 공통 규칙

[common.md](common.md) 기준으로 대부분의 API는 다음 공통 헤더를 사용합니다.

| Header | 필수 | 의미 | 구현 메모 |
| --- | --- | --- | --- |
| `api-id` | Y | 호출할 API ID | 예: `ka10095`, `ka10080` |
| `authorization` | Y | `Bearer <token>` | [001-au10001.md](apis/001-au10001.md) 결과의 `token` 사용 |
| `cont-yn` | N | 연속조회 여부 | 응답 Header가 `Y`일 때 다음 페이지 요청에 사용 |
| `next-key` | N | 연속조회 키 | 응답 Header의 `next-key`를 다음 요청에 전달 |

응답 Body에는 대체로 `return_code`, `return_msg`가 포함됩니다. 오류 처리는 [error-codes.md](error-codes.md)를 기준으로 분기합니다.

## 값 파싱 주의점

원문 예시 응답을 보면 가격, 등락, 거래량 값이 대부분 `String`입니다. 숫자로 비교하려면 반드시 정규화 계층을 둡니다.

| 패턴 | 예 | 처리 |
| --- | --- | --- |
| 부호가 붙은 가격 | `+156600`, `-78800` | 부호 제거 후 숫자화하되, 키움의 부호 의미가 가격 방향인지 값 자체의 음수인지 필드별로 확인 |
| 비율 문자열 | `+28.68`, `-0.24` | `decimal` 또는 고정소수점으로 변환 |
| 빈 문자열 | `""` | `null` 처리 |
| 시간 문자열 | `163713`, `20250917132000` | `HHmmss` 또는 `yyyyMMddHHmmss`로 파싱 |
| 시장 접미사 | `039490_NX`, `039490_AL` | KRX/NXT/SOR 선택을 명시적으로 저장 |

## 필수 API 상세

### 1. 접근토큰 발급: `au10001`

- 문서: [001-au10001.md](apis/001-au10001.md)
- 호출: `POST /oauth2/token`
- Body 필수값: `grant_type`, `appkey`, `secretkey`
- 응답 핵심값: `token`, `token_type`, `expires_dt`
- 서비스 역할: API 클라이언트 시작 시 토큰을 발급하고, 만료 전에 갱신합니다.

구현 포인트:

- 원문 예시의 `expires_dt`는 `yyyyMMddHHmmss` 형태입니다.
- 토큰은 메모리와 안전한 저장소 중 하나에 보관하되, 로그에 남기지 않습니다.
- 토큰 오류는 [error-codes.md](error-codes.md)의 `8003`, `8005`, `8010`, `8031`, `8103` 계열로 분기합니다.

### 2. 여러 종목 현재가 조회: `ka10095`

- 문서: [087-ka10095.md](apis/087-ka10095.md)
- 호출: `POST /api/dostk/stkinfo`
- Body 필수값: `stk_cd`
- 특징: `stk_cd`에 여러 종목코드를 `|`로 구분해 입력할 수 있습니다.

예:

```json
{
  "stk_cd": "005930|000660|035420"
}
```

가격 알림 MVP의 기본 조회 API로 봅니다. 응답 Body의 `atn_stk_infr[]`가 종목별 현재 상태 목록입니다.

| 응답 필드 | 의미 | 알림 조건 사용 |
| --- | --- | --- |
| `stk_cd` | 종목코드 | 종목 식별 |
| `stk_nm` | 종목명 | 알림 메시지 |
| `cur_prc` | 현재가 | 목표가 돌파/이탈 |
| `base_pric` | 기준가 | 기준 가격 비교 |
| `pred_pre` | 전일대비 | 전일 대비 금액 조건 |
| `pred_pre_sig` | 전일대비기호 | 상승/하락 방향 판단 |
| `flu_rt` | 등락율 | 등락률 조건 |
| `trde_qty` | 거래량 | 거래량 급증 조건 |
| `trde_prica` | 거래대금 | 거래대금 조건 |
| `cntr_qty` | 체결량 | 체결 강도 보조 판단 |
| `cntr_str` | 체결강도 | 수급/강도 조건 |
| `sel_bid`, `buy_bid` | 매도/매수호가 | 최우선 호가 알림 |
| `open_pric`, `high_pric`, `low_pric`, `close_pric` | OHLC | 당일 가격 범위 조건 |
| `cntr_tm` | 체결시간 | 데이터 최신성 확인 |

구현 포인트:

- 감시 종목의 1차 폴링은 이 API 하나로 처리합니다.
- 모든 종목에 상세 API를 붙이지 말고, 이 결과로 조건 근처 여부를 먼저 판단합니다.
- 호출 제한 수치가 명시되어 있지 않으므로 배치 크기와 초당 요청 수는 설정값으로 둡니다.

## 조건부 보강 API

### 분봉 조건: `ka10080`

- 문서: [077-ka10080.md](apis/077-ka10080.md)
- 호출: `POST /api/dostk/chart`
- Body 필수값: `stk_cd`, `tic_scope`, `upd_stkpc_tp`
- Body 선택값: `base_dt`
- 응답 목록: `stk_min_pole_chart_qry[]`

`tic_scope` 값:

| 값 | 의미 |
| --- | --- |
| `1` | 1분 |
| `3` | 3분 |
| `5` | 5분 |
| `10` | 10분 |
| `15` | 15분 |
| `30` | 30분 |
| `45` | 45분 |
| `60` | 60분 |

주요 응답 필드:

| 필드 | 의미 | 사용처 |
| --- | --- | --- |
| `cur_prc` | 분봉 종가 | 분봉 기준 가격 조건 |
| `trde_qty` | 해당 봉 거래량 | 거래량 급증 |
| `cntr_tm` | 체결시간 | 봉 시각 |
| `open_pric`, `high_pric`, `low_pric` | 분봉 OHLC | 돌파/이탈 조건 |
| `pred_pre`, `pred_pre_sig` | 전일대비, 기호 | 방향성 판단 |

판단:

- 종목별 호출이므로 감시 종목이 많으면 비용이 빠르게 증가합니다.
- 기본 현재가 알림에는 사용하지 말고, 사용자가 분봉 조건을 등록한 종목에만 호출합니다.

### 단일 종목 상세 시세: `ka10007`

- 문서: [012-ka10007.md](apis/012-ka10007.md)
- 호출: `POST /api/dostk/mrkcond`
- Body 필수값: `stk_cd`
- 응답 성격: 현재가, 전일종가, 거래량, 거래대금, 예상체결, 10단계 호가가 넓게 포함됩니다.

알림 서비스에서 유용한 필드:

| 필드 | 의미 |
| --- | --- |
| `cur_prc` | 현재가 |
| `pred_close_pric` | 전일종가 |
| `flu_rt` | 등락률 |
| `pred_rt` | 전일비 |
| `trde_qty` | 거래량 |
| `trde_prica` | 거래대금 |
| `exp_cntr_pric`, `exp_cntr_qty` | 예상체결가/수량 |
| `sel_1bid`~`sel_10bid` | 매도 1~10호가 |
| `buy_1bid`~`buy_10bid` | 매수 1~10호가 |
| `sel_1bid_req`~`sel_10bid_req` | 매도 호가잔량 |
| `buy_1bid_req`~`buy_10bid_req` | 매수 호가잔량 |

판단:

- `ka10095`보다 응답 범위가 넓지만 단일 종목 조회 성격입니다.
- 목표가 근처, 거래량 급증, 호가 확인이 필요한 종목에만 추가 확인용으로 씁니다.

### 호가 전용 조건: `ka10004`

- 문서: [009-ka10004.md](apis/009-ka10004.md)
- 호출: `POST /api/dostk/mrkcond`
- Body 필수값: `stk_cd`
- 응답 성격: 10단계 매도/매수 호가, 잔량, 직전대비, 총잔량, 시간외 잔량

알림 서비스에서 유용한 필드:

| 필드 | 의미 |
| --- | --- |
| `bid_req_base_tm` | 호가잔량기준시간 |
| `sel_fpr_bid`, `sel_fpr_req` | 최우선 매도호가/잔량 |
| `buy_fpr_bid`, `buy_fpr_req` | 최우선 매수호가/잔량 |
| `sel_2th_pre_bid`~`sel_10th_pre_bid` | 매도 2~10차선 호가 |
| `buy_2th_pre_bid`~`buy_10th_pre_bid` | 매수 2~10차선 호가 |
| `tot_sel_req`, `tot_buy_req` | 총매도/총매수잔량 |
| `ovt_sel_req`, `ovt_buy_req` | 시간외 매도/매수잔량 |

판단:

- 단순 현재가 알림에는 과합니다.
- “매수 1호가가 특정 가격 이상”, “총매수잔량이 총매도잔량보다 N배 이상” 같은 호가 기반 조건을 추가할 때 사용합니다.

### 일봉 조건: `ka10086`

- 문서: [083-ka10086.md](apis/083-ka10086.md)
- 호출: `POST /api/dostk/mrkcond`
- Body 필수값: `stk_cd`, `qry_dt`, `indc_tp`
- 응답 목록: `daly_stkpc[]`

주요 응답 필드:

| 필드 | 의미 |
| --- | --- |

| `open_pric`, `high_pric`, `low_pric`, `close_pric` | 일봉 OHLC |

## 종목 마스터 API

- 이미 `ka10099` 캐시가 최신이면 캐시로 1차 검증하고, 필요할 때만 보강 호출합니다.

## 오류와 호출량 제어

[error-codes.md](error-codes.md)에서 가격 알림 서비스가 먼저 분기해야 할 오류는 다음입니다.

| 코드 | 메시지 요지 | 처리 |
| --- | --- | --- |
| `1511` | 필수 입력값 누락 | 요청 생성 버그로 보고 즉시 로깅 |
| `1513`~`1516` | authorization 헤더 문제 | 토큰 형식/누락 확인 |
| `1517` | 입력값 형식 오류 | 종목코드, 날짜, 구분값 검증 |
| `1687` | 재귀 호출 제한 | 재시도 루프 차단 |
| `1700` | 허용된 요청 개수 초과 | 호출 속도 감속, 백오프, 배치 축소 |
| `1901` | 시장 코드 없음 | 종목코드/시장 접미사 검증 |
| `1902` | 종목 정보 없음 | 사용자 입력 종목 거부 |
| `8001`~`8002` | App Key/Secret 검증 실패 | 설정 오류로 처리 |
| `8003`, `8005`, `8009`, `8010`, `8031`, `8103` | 토큰 발급/조회/유효성/IP/투자구분 문제 | 토큰 재발급 또는 운영/모의 설정 확인 |
| `8104` | 모의투자 미지원 API | 실전/모의 지원 여부 표시 |

`1700` 처리 정책:

```text
1700 발생
  -> 현재 API ID의 호출 중단
  -> 백오프 대기
  -> 초당 요청 수 감소
  -> 반복 발생 시 배치 크기 감소
  -> 관리자 경고
```

설정값으로 분리할 값:

```text
KIWOOM_MAX_REQUESTS_PER_SECOND
KIWOOM_BATCH_SIZE
KIWOOM_POLL_INTERVAL_SECONDS
KIWOOM_BACKOFF_SECONDS
KIWOOM_ALERT_COOLDOWN_SECONDS
```

## 권장 데이터 흐름

```text
서비스 시작
  -> au10001 접근토큰 발급
  -> ka10099 시장별 종목 목록 로드 또는 로컬 캐시 사용
  -> 사용자가 등록한 종목을 ka10100으로 검증

스케줄러 실행
  -> 감시 종목을 배치로 나눔
  -> ka10095로 배치 현재가 조회
  -> 숫자/시간/빈 문자열 정규화
  -> 알림 조건 평가
  -> 조건 근처 종목만 ka10080/ka10007/ka10004/ka10086 추가 조회
  -> 중복 알림 쿨다운 확인
  -> 알림 발송
  -> 마지막 가격과 알림 상태 저장

오류 발생
  -> 1700이면 호출 속도 감속
  -> 토큰 오류면 토큰 재발급
  -> 입력 오류면 해당 종목 또는 조건 비활성화
  -> 네트워크 오류면 재시도와 백오프
```

## 호출 전략

### 소규모 감시

감시 종목이 1~30개 정도라면 다음 구조로 시작합니다.

```text
매 1분:
  ka10095 관심종목정보요청
  -> 모든 감시 종목 현재가 수집
  -> 조건 판단
  -> 필요한 경우 알림 발송
```

### 중간 규모 감시

감시 종목이 많아지면 종목을 배치로 나눕니다.

```text
watchlist = [종목 1..N]
batch_size = 실측으로 결정
interval = 60초

매 interval:
  watchlist를 batch_size 단위로 분할
  각 배치를 일정 간격으로 순차 호출
```

예를 들어 120개 종목을 4개 배치로 나누면, 1분마다 4번 호출하는 구조가 됩니다.

### 상세 조회는 조건부로만

```text
ka10095 결과에서:
  목표가 근처
  등락률 조건 근처
  거래량 급증
  호가 조건이 걸려 있음
  데이터 시간이 비정상

이 경우에만:
  ka10080, ka10007, ka10004, ka10086 중 필요한 API 추가 호출
```

모든 종목에 상세 API를 매번 붙이면 호출량이 쉽게 커집니다.

## 알림 중복 방지

최소한 다음 상태를 저장합니다.

| 값 | 설명 |
| --- | --- |
| `last_price` | 마지막 조회 가격 |
| `last_seen_at` | 마지막 조회 시각 |
| `last_notified_price` | 마지막 알림 가격 |
| `last_notified_at` | 마지막 알림 시각 |
| `last_condition_key` | 마지막으로 만족한 조건 |
| `condition_active` | 현재 조건 충족 상태 |

예:

```text
삼성전자 현재가 >= 80000 조건

09:10 80100 -> 알림 발송
09:11 80200 -> 쿨다운 중이면 발송 안 함
09:30 79900 -> 조건 해제
10:05 80100 -> 다시 조건 진입, 알림 발송 가능
```
