호출 제한은 약관상 **제11조 API 호출 횟수 제한**과 **제8조/제9조 비정상 조회 부하**를 같이 봐야 합니다.

약관에 적힌 제한은 이렇습니다.

| 구분 | 제한 |
|---|---:|
| 조회 요청 | 초당 5건 |
| 주문 요청 | 초당 5건 |
| 실시간 조건검색 | 로그인 1개당 10건 |

즉, REST API를 쓸 때 **조회 API와 주문 API 각각 초당 5건 이하**로 맞춰야 한다는 의미입니다. 조회와 주문을 합쳐서 5건인지, 각각 5건인지는 문구상 “조회횟수 초당 5건 / 주문횟수 초당 5건”으로 나뉘어 있어 각각으로 읽히지만, 실제 서버 정책은 더 보수적으로 잡는 게 안전합니다.

특히 주의할 상황은 이겁니다.

1. **여러 종목을 반복 조회하는 경우**
   - 예: 20종목 현재가를 1초마다 조회하면 초당 20건이 되어 제한 초과 가능성이 큽니다.
   - 20종목이면 최소 4초 이상에 나눠 조회하는 식으로 설계해야 합니다.

2. **자동매매에서 주문을 여러 번 나누는 경우**
   - 매수/매도/정정/취소 주문도 주문 호출로 잡힐 가능성이 큽니다.
   - 급등락 때 로직이 반복 주문을 내면 초당 5건을 넘기기 쉽습니다.

3. **재시도 로직**
   - API 실패 시 즉시 재시도하면 호출 제한을 더 빨리 초과합니다.
   - 실패하면 200ms, 500ms, 1초 식으로 간격을 두고 재시도하는 게 안전합니다.

4. **비정상적인 데이터 조회 부하**
   - 제8조에 따르면 비정상적인 데이터 조회로 부하가 발생하면 **1개월 이용 중지**될 수 있습니다.
   - 제9조에 따르면 이런 부하가 **3회 이상 발생하면 이용 해지**될 수 있습니다.
   - 단순히 “초당 5건 넘으면 에러” 수준이 아니라, 반복되면 계정 단위 제재로 이어질 수 있다는 점이 중요합니다.

5. **실시간 조건검색**
   - “로그인 1개당 10건”이라고 되어 있으므로, 한 로그인 세션에서 조건검색을 10개 넘게 돌리는 구조는 위험합니다.
   - 조건검색을 많이 쓰는 전략이면 조건 수를 줄이거나, 조건 통합을 고려해야 합니다.

개발할 때는 이렇게 잡는 게 좋습니다.

```text
조회 API: 초당 최대 4건 이하로 제한
주문 API: 초당 최대 3~4건 이하로 제한
재시도: 즉시 재시도 금지, 지수 백오프 적용
대량 조회: 종목을 큐에 넣고 순차 처리
자동주문: 중복 주문 방지 키, 쿨다운, 일일 주문 횟수 제한 설정
```

실무적으로는 초당 5건을 꽉 채우기보다 **초당 4건 정도로 여유를 두는 것**이 안전합니다. 서버 시간 기준, 네트워크 지연, 병렬 요청, 재시도 때문에 내 프로그램에서는 5건으로 보였는데 서버에서는 초과로 잡힐 수 있습니다.
